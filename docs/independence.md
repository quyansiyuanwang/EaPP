# 独立性实验

本文件记录一次实验：**规范正文本身是否足够写出一份实现？**

它不是规范的一部分。与规范冲突时以规范为准。

**实验的完整产物** —— 两份实现、各自的测试、桥接脚本、三次交叉运行的原始日志 ——
在 `independence` 分支的 `experiment/` 下。主仓库只保留本文件给出的方法、数字与结论。

---

## 1. 为什么需要这个实验

`GOVERNANCE.md` §1 把项目的完成定义成一句话：

> 一个没有读过本仓库任何代码的第三方，只读 `docs/spec/eapp.md`，能够写出一份实现，
> 并据此为它的插件作者提供一套只经由 §51 的操作完成组合、互动与调用的表面。

这句话可以自证，也可以被检验。自证的方式是"我读了正文，我觉得够"—— 那是作者的判断，
而作者恰好是写正文的人。检验的方式只有一个：**找一个没读过这份仓库的人，只给他正文，
看他能不能写出实现。**

在此之前，本项目依赖的是 `reference` 分支上的两份实现。那一次的证据强度有边界：
两份实现的作者被禁止互相阅读，但**没有任何办法在事后证明他们确实没读过**。
结构上的信号（词表、文件划分、类型命名都不同）与独立编写一致，但那是旁证。

## 2. 怎么做的

两次实现由两个独立代理并行完成，彼此不可见。

**隔离。** 每个实现者只被允许读一个文件：`docs/spec/eapp.md`。明确禁止：
`docs/rationale.md`、`docs/guides/`、`docs/reference/`、`README.md`、`GOVERNANCE.md`、
`CHANGELOG.md`、`rfcs/`、`docs/STYLE.md`、`reference` 分支的任何内容、对方的目录、网络检索。

禁读清单是这次实验的全部价值所在。歧义是数据 —— 一个实现者遇到的每一处不确定，
都说明正文在那一处没有把话说死；去别处找答案会让这份数据消失。

**共同的接口约定。** 双方都必须导出 `createRuntime()`，其成员是 §51 表格里的操作名。
这不是协议要求，是实验装置：规范不规定模块布局，因此两个实现需要一处**中立的接缝**
才能被交叉运行。接缝只约定"操作在哪个对象上"，不约定任何语义。

**交叉验证。** 各自写测试，测试同样只依据正文。然后：

```
甲的测试 跑在 乙的实现上
乙的测试 跑在 甲的实现上
```

这才是判定。一份实现通过自己的测试，只说明它自洽；两个互不相识的作者，
用各自从同一段正文推出的测试去考对方的实现，通过与否才是正文够不够的证据。

## 3. 结果

### 3.1 两侧的产出

| | 覆盖范围 | 实现 | 测试 | 自己的测试是否全绿 |
|---|---|---|---|---|
| **甲** | 第 I、II、IV 部分（不含 State Mode） | 1,422 行 | 10 个文件 | **否** —— 未在预算内收敛，其中一个文件会挂起 |
| **乙** | 第 I 部分（Composition Core） | 415 行 | 10 个用例 | **是**，10 / 10 |

**甲未能收敛这一事实必须写在这里，因为它限定了下面数字的强度。** 甲写了远多于乙的代码与测试，
但它的测试套件在预算耗尽时仍未全绿，因此「甲的测试」并不完全等于「甲的规范理解」——
其中一部分断言反映的是甲尚未实现完的意图，而不是它对正文的读法。

### 3.2 交叉运行

**原始交叉运行：两侧都在第一行失败。**

```
甲的测试 → 乙的实现     乙的实现上没有 registerPlugin
乙的测试 → 甲的实现     甲的实现上没有 register
```

两个实现者都独立报告：**规范从未说明 Plugin 如何进入运行时**。他们各自发明了一个入口，
名字不同、描述符形状也不同 —— `registerPlugin({ identity })` 对 `register({ domain, id, instance })`。
这不是谁理解错了，是正文没有写。

**手工桥接那一个缺口之后，再跑一次。** 桥接只翻译装载调用，不动任何行为：

```
甲的 Core 测试（6 个文件）→ 乙的实现      21 通过 / 52 失败
```

也就是说：**即使把唯一未定义的那一处接上，两份实现仍不可互换。** 失败集中在正文没有写下的
形状上 —— 返回的对象里有哪些字段、`bind` 的结果是快照还是活视图、`watch` 的"流"是什么形状。

### 3.3 结论

**正文不足以让两个独立实现互相替代。** 这一条是可判定的，而且它在第 I 部分就已经成立 ——
不需要等到 Interaction 或 State。

但结论**不是**"规范没用"。两个实现者在同一段正文上达成了大量一致（乙的 10 个用例在甲的实现上、
甲的 21 条断言在乙的实现上通过），而这些一致**不是靠沟通达成的**。可互换需要的是更强的性质：
正文不仅要说清每条规则，还要说清每个被命名的东西**长什么样**。

## 4. 这次实验的产物

- `3.6.0`：装载面（§8.4）、`PluginRef` 的字段表、`OP-4` / `OP-7` / `OP-9` 的修正、
  §53 与附录 D 的内部矛盾。**这些全部来自实验，不是来自设计。**
- `rfcs/0002` 与 `rfcs/0003` 各收到一份独立实现者的评审（§2.3 要求两份）。
- 两份评审指出的其余缺口，逐条列在两份提案的「未解决的问题」里。

## 5. 这次实验证明不了什么

- **它不能证明两位实现者确实没有互相偷看。** 隔离以禁令与工作目录实现，我在事后只能确认
  他们各自的产出里没有对方的痕迹，不能确认过程。这一点与 `reference` 分支那次实验的限制相同，
  只是这次多了一层：他们的**测试**也来自正文，因此"通过对方的测试"比"通过自己的测试"强得多。
- **它不能替代评审。** 两位实现者提供的是评审意见，不是对"规范正确"的背书；
  §2.3 要求的两份评审只取得了一份，另一份仍缺。
- **甲未收敛，因此 52 次失败里混有甲的未完成之处。** 一个更干净的版本应当先让两侧各自的
  测试全绿，再交叉运行。这一次的时间没有用在这里，是本次实验最明显的缺陷。
- **它只覆盖第 I 部分（交叉运行）**，以及甲的自我验证覆盖第 II、IV 部分。
  第 III 部分（State Mode）完全没有被这次实验触及。
