# 设计依据

本文件记录**每条规则为什么不是别的样子**。规范只陈述规则是什么；
没有这一份，下一个维护者会把同样的错误再犯一遍。

它不是规范的一部分。与规范冲突时以规范为准。

---

## 1. 为什么是协议而不是框架

规范规定语义，不规定实现。这条选择的代价在开头就付出了：不能提供一个"直接能用"的运行时，
因此第三方必须自己写一份实现才能让插件跑起来。

换来的是分层方向可被检查。**Composition Core → Interaction Layer → State Mode → Transport**
单向依赖，下层 MUST NOT 定义上层语义（§1.1）。这条约束使每一层可以独立替换：
换掉 Transport 不影响 Binding 的派生规则，换掉实现语言不影响任何一层的语义。

一条反例足以说明它为什么值得：如果 Transport 可以定义投递语义，那么换一种传输就会改变
`at-least-once` 的含义，而"任何传输只要实现这些语义就能互通"随之不成立。

## 2. 为什么三层合并为一份正文

三层曾各自冻结，文件名是"冻结标识符"（`v3.0.0-core` 等），与协议版本不是同一个号。
那套制度的代价在两处显现：

- **读者必须先读变更记录**才能知道当前协议版本，因为文件名回答不了。
- **不变量标识符可以在两层里指不同的规则。** `L-1` 在 Composition Core 是 Lifecycle 的
  `activate`，在 Interaction Layer 是 Lease 的唯一性；`CH-1` 在一处是"Channel 边界"，
  在另一处是"一个 Channel 对应恰好一个 Binding"。
  第二处直到合并时才发现 —— 当时的检查工具把"逐文件检查、从不全局检查"写进了注释，
  于是这个冲突被一条注释合法化了。

合并之后协议版本是唯一的版本号，不变量标识符在整个协议范围内唯一。
旧文本以标签 `spec-3.3.0` 锚定，不再随工作分支演进。

**版本由标签承载，不由文件名承载。** 一个把版本写进文件名的规范，会迫使读者在打开它之前
先弄清楚文件名与当前版本的关系。

## 3. 为什么规范的语言是中立记法

规范曾用 TypeScript 表达接口，共约 455 行代码块，而开篇宣称"任何语言、任何运行时、
任何传输，只要实现这些语义，就能互通"。这两句话不能同时成立：语言中立是宣称，
带语言标注的代码块是文本事实。

现在操作签名用 `op(args) -> result`，数据结构用逐字段表格，无语言标注的代码块 ——
由 `check:spec` 强制。

**签名不标注异步性。** 一个操作是否 MUST 在返回之前完成其语义效果，由该操作的条款规定；
把 `Promise` 写进签名会把一个实现细节升格为协议要求。这一条不是形式问题：
早期版本里 `watch()` 的同步 / 异步形态在规范与实现之间不一致，而这个分歧只被
`SUB-9`（初始位置必须是具体值）间接逼出来过。

## 4. 为什么 Revision 就是日志位置

`Revision` 曾是 per-cell 的版本号，于是它既不是全序，也无法充当 `Cursor`，
而"从某个位置之后读取变更"这类操作全都依赖于一个全序。

现在二者是**同一域上的同一类型**：一次写入在 Channel 日志尾部追加一条记录并获得一个位置，
这个位置同时是本次写入的 `Revision` 和可用的 `Cursor`。

推论：`REV-7`（Revision 在 State Mode 中可作 Cursor）不再是一条例外，而是 `CR-1` 的推论。

## 5. 为什么删除是一等原语

`delete` 曾是 `set({ deleted: true })`。这使一次删除看起来像一次普通写入，
于是边界情况无法定义：重复删除是否分配新的 revision、是否产生变更、是否通知观察者。

现在 `delete` 是 Transport 的一等操作，no-op 有明确定义（不分配 revision、
不产生变更、不通知，§40.3），返回值恒为操作完成后该 key 的当前 revision（§40.4）。

**已逻辑删除的 cell MUST 被 `get` 返回**（`SC-6`）：no-op 分支要求调用方拿得出旧 revision，
若 `get` 对已删除返回空，那条分支永远不可达。

## 6. 为什么 `maxRevision` 在 cells 之前读取

若 `cells` 与 `maxRevision` 来自同一次读取，`cell.revision <= maxRevision` 是**恒真式** ——
检查它会永远通过，而它检查不出任何东西。

把 head 的读取放到 cell 读取**之前**（§43.2），打开一个真实的竞态窗口，
使 `SNAP-1` 可被违反、因而可被测试。这条改动是"不变量必须可判定"的一个具体落点：
一条恒真的不变量在闸门眼里和一条完整的不变量没有区别。

## 7. 为什么取消 CRDT 的能力豁免

CRDT 曾获得"最终一致但可以支持状态"的豁免。问题是：CAS 的正确性建立在全序之上。
一个最终一致却号称支持 CAS 的存储会**静默丢更新**，而"静默丢更新"是本协议最不该容忍的失败模式。

现在能力标志收紧：revision 顺序不是全序的实现 MUST 声明 `supportsStateRevision = false`，
MUST 声明 `stateConsistency = 'eventual'`，MUST NOT 声称支持 CAS（`TS-4`）。
于是 `set` / `delete` 直接失败，而不是悄悄退化成后写覆盖。

## 8. 为什么错误模型分三层扩展，对象只定义一个

三层的错误码各自扩展（附录 D），但错误对象 MUST 在实现内只定义一次、三层共用（§18）。

若三层各自声明一个同名结构而不定义如何构造它，错误的产生将无从成立 ——
这在早期版本中真实发生过：三份文档各写一个 `interface EappError`，没有一处是类。

`retryable` 的赋值只有一条规则值得记：`EAPP_REVISION_CONFLICT` 为真（CAS 冲突可重试），
其余为假。默认假是刻意的 —— 把可重试与不可重试混在一起，会让调用方对不可重试的失败重试。

## 9. 为什么新增插件开发表面

在表面出现之前，语义相同的两份实现仍可能无法互通：`find` 还是 `discover`、
`bind` 的第二个参数是引用还是 id、超时返回什么、`invoke` 的 `from` 指哪一方。

这不是假想。本项目自己的两份实现之间已经发生过三次这类分歧，其中一次是 Go 实现者
依规范正文独立实现 Interaction 层时被迫自行裁定的 **10 处留白** ——
ConsumerGroup 的起始位置、`at-most-once` 下 `ack` 的语义、`resume` 是否回退。
这些裁定都合理，但没有一条写进规范，于是两份实现在同一批检查下同时通过，
靠的是一批未记录的默契。

**表面不是第四层**（§50）。它不含新的本体，只把前三部分已经要求过的操作在形状上钉死。
把它做成第四层会改变分层方向，那属于 `4.0.0`，且没有任何语义上的必要。

## 10. 为什么实现与检查工具移出主仓库

主仓库曾装着 2,275 行规范、26,900 行实现与闸门，比例约 1 : 12；
而项目的"完成"定义是"规范冻结 + 一致性全绿 + 至少两份独立实现过同一批外部检查" ——
那是实现项目的完成定义。

规范是产品这一条写在了引言里，却没有写进完成定义，于是**产品的规模被验证材料的规模掩盖**。
现在主仓库只含规范与文档；证据在 `reference` 分支上，仍然完整。

**独立性以过程保证，不能事后证明。** 第二份实现的作者被明确禁止阅读第一份；
没有独立的方法在事后验证它确实没有读过。结构上的信号（词表、文件划分、类型命名都不同）
与独立编写一致，但那是旁证。

**后来的实验把这件事推进了一步。** `docs/independence.md` 记录了一次可复现的版本：
两个实现者只读正文、彼此不可见，各自写出实现与测试，然后把**一方的测试跑在另一方的实现上**。
通过与否不依赖任何人的自述 —— 那是行为证据，而不只是结构旁证。
它给出的结论也比"看起来是独立写的"更硬：**正文当时不足以让两个实现互相替代**，
于是有了 `3.6.0`。

## 11. 为什么参考页不复述规范

参考页原先逐字段复述规范的类型定义，因此需要一道闸门比对复述与正文的成员类型 ——
那个闸门存在的唯一理由就是这份复述。

删掉复述之后，参考页成为索引页：实体是什么、规则写在哪、最容易和什么混淆。
字段表只有一份，在规范里。复述是一种债务：它不产生信息，只产生一个会与正文分叉的副本。

## 12. 为什么闸门检查规范自己

实现移出之后，主仓库能检查的只剩文本。这不是退步 —— 一个仓库能对自身产品做出的判定，
本来就应该是最多的。

`check:spec` 的七条规则里，有四条在写成当天就抓出了真实缺陷：

- **章节引用**抓出两处指向不存在的 `§3.5` / `§4.4`，以及一句关于已删除的 `§1` 的话。
- **`UNSTATED`** 抓出两个分卷里共 12 条只存在于汇总清单、正文从未陈述的不变量。
- **语言中立**抓出两处规范正文点名 TypeScript 包的地方 —— 而那正是它要求读者去读代码的两处。
- **附录 B 的声明块**抓出四处仍带旧编号的引用：`ConsumerGroup（§8）` 指向 Plugin，
  `Request 模式（§3）` 指向版本规则。它们能解析，因此引用规则看不见它们 ——
  一条规则能验证"指向存在"，验证不了"指向正确"。

最后一条值得单独记下来：它是本项目里唯一一类**闸门自身无法覆盖**的缺陷。
写规范的人仍然要逐处确认引用指向的是正确的小节。
