# 文档标准

本文件规定 EaPP 仓库里**怎么写文档**。它是规范性约定 —— 违背它的文档会被要求返工。

---

## 1. 文档分层

这是最重要的一条规则。**规范性**与**非规范性**是硬边界。

```
规范性（normative）       docs/spec/
                         「规则是什么」。唯一裁决者。冲突时以它为准。

非规范性（non-normative） docs/reference/ · docs/guides/ · docs/rationale.md
                         「规则怎么用」「为什么这样定」。解释、索引、举例。
```

由此推出三条禁令：

- **非规范性文档 MUST NOT 引入新规则。** 写参考页时若发现某条语义无处可依，
  那说明规范缺一条 —— 去补规范，不要在文档里发明它。
- **非规范性文档 MUST NOT 逐字复制规范正文。** 复制会分叉；
  规范改了而复制没改，读者就拿到了两个互相矛盾的"权威"。
- **规范性正文 MUST 单独可读。** 它 MUST NOT 依赖任何 `docs/spec/` 之外的文件，
  也 MUST NOT 链接到外部。`check:spec` 检查这两条。

---

## 2. 四种文档各自的职责

| 文档 | 读者的问题 | 组织方式 | 允许推测吗 |
|---|---|---|---|
| `docs/spec/eapp.md` | 规则是什么？ | 按协议结构 | 否，MUST / MUST NOT |
| `docs/reference/` | 这个实体是什么，规则写在哪？ | **按实体**，一实体一页 | 否，只索引 |
| `docs/guides/` | 我要做 X，怎么做？ | **按任务** | 可以，但须标注 |
| `docs/rationale.md` | 为什么这样定，为什么不是别的样子？ | 按规范小节 | 否，只记录已作出的裁定 |

**参考页与指南都不许说"应该可以"。** 只有两种状态：规范里写了、规范里没写。

---

## 3. 参考页是索引页

`docs/reference/` 的每一页**不复述规范**。规范已经给了字段表与签名；参考页的作用是让人在
30 秒内回答三个问题：**它是什么 / 规则写在哪 / 它最容易和什么混淆。**

固定结构，每页不超过 60 行：

```
标题              实体名
一句话            它是什么
元数据表          层 · 规范小节 · 不变量前缀 · 稳定度
语义              3–8 行，只解释规范说了什么
常见误用          1–4 条，每条给出规范中的依据
相关              指向其他实体页与规范小节
```

**为什么不再复述类型。** 参考页原先逐字段复述规范的类型定义。复述会漂移：规范一改，
复述就成了假话，而读者没有任何理由怀疑它。曾经有一道闸门专门比对复述与正文的成员类型 ——
那道闸门存在的唯一理由就是这份复述。删掉复述，闸门与它监视的风险一起消失。

模板见 [`docs/reference/_TEMPLATE.md`](reference/_TEMPLATE.md)。

## 4. 每条规则：正文陈述，以及实现的测试

一条不变量有两种合法状态，分属两侧：

| 侧 | 要求 | 由谁强制 |
|---|---|---|
| 规范 | 附录 B 声明的每个 ID MUST 也在正文中被陈述 | `check:spec` 的 `UNSTATED` |
| 实现 | 每个不变量 MUST 至少有一个对应的测试用例（§3.1） | 实现方的测试套件 |

**只在附录 B 的清单里出现、正文中没有对应陈述的标识符，是一个读了像规则的编号。**
它会被读者和闸门一并当作完整的不变量 —— 这在本项目历史上发生过两次：一次丢掉两条，
一次丢掉十条。因此 `UNSTATED` 是闸门，不是建议。

测试那一侧不属于本仓库：实现已经移出，`docs/spec/` 不再随附测试。

---

## 5. 语言与语气

- **正文中文；标识符、代码、RFC 2119 用语保持英文。**
  写 `MUST` / `SHOULD` / `MAY`，不写"必须"/"应该"—— 它们是术语，不是修辞。
- **不使用第二人称。** 不写"调用方可以……"，直接写"调用方 MUST 先……"。
  规范语气描述的是约束，不是建议。
- **一句话一个判断。** 中文长句在规范里是债务。
- **不用夸张词。** 不写"极其强大"、"完美解决"。协议文档要能被信任。
- **不写否定式排比。** "不是 A，不是 B，不是 C"用三次否定定义一件事，
  读者得自己推出正面说法。直接给分类。

`check:docs` 会拒绝第二人称、若干口语标记与否定式排比。它检查的是**无歧义的标记**，不是文风的全部；
判断性的部分仍然靠评审。

---

## 6. 交叉引用

- 提到规范条款时，给出**具体小节号**（`§26.2`），不是"详见规范"。
- 非规范性文档提到实现或示例时，只能是外部 URL（`reference` 分支），
  因为那些路径不在本分支上。相对链接指向不存在的文件会被 `check:docs` 拒绝。
- 外部 URL 不检查 —— 网络失败不该让 `verify` 因为与本次改动无关的原因变红。

---

## 7. 示例

- **示例 MUST 与规范的语言中立化一致。** 规范用 `op(args) -> result` 的中立记法与逐字段表格，
  其中没有任何语言标注的代码块。指南中的示例也应如此；确需给出具体语言的写法时，
  那一段必须紧邻一句说明它是某一份实现的选择，而非协议要求。
- **不得使用真实的、依赖某个包的导入路径。** 本仓库不含实现，任何 `import … from '@eapp/…'`
  都是假话。
- **不确定的地方要写出来。** 示例不是宣传材料：若某条语义有代价，
  示例与指南都要直说。

---

## 8. 目录与命名

```
docs/spec/       固定名           eapp.md —— 不带版本号，版本由元信息与标签承载
docs/reference/  小写短横线，实体名 identity.md · consumer-group.md · state-cell.md
docs/guides/     小写短横线，动词短语 write-a-plugin.md · getting-started.md
```

`_` 前缀表示模板，**不进索引**。

---

## 9. 修改文档时同步什么

| 改了 | 必须同时更新 |
|---|---|
| 规范条款 | `CHANGELOG.md` + 受影响的 `docs/reference/` 页面 + `docs/guides/` 中复述过该内容的页面 |
| 不变量 ID | 正文、附录 B、以及实现方的测试名 |
| 新增实体 | `docs/README.md` 的索引表 + 参考页 + 规范小节 |
| 语义变更 | 先走 `rfcs/`；依据写入 `docs/rationale.md` |

---

## 10. 闸门

文档不是靠自觉维持的。仓库里的两个闸门：

```bash
npm run check:spec   # 规范自洽
npm run check:docs   # 文档
```

| 闸门 | 检查什么 |
|---|---|
| 章节编号 | 二级标题从 1 到 N 连续，无缺号、无重号 |
| 章节引用 | 每处 `§N` / `§N.M` 解析到真实存在的小节 |
| 不变量 | 附录 B 声明的每个 ID 也被正文陈述；无重复声明 |
| 自足性 | 规范性正文不链接到 `docs/spec/` 之外 |
| 语言中立 | 规范性正文不出现实现名（`@eapp/`、`packages/` 等），也没有语言标注的代码块 |
| 链接 | 每条相对链接落到真实文件 |
| 语域 | 代码块之外不出现第二人称、口语标记或否定式排比（§5） |

**每一条都曾经在无人执行的情况下失效过。** 章节引用这一条上线时当场抓出了三处：
一处指向从未存在的 `§3.5`，两处指向没有子节的 `§4.4`，以及一句声称勘误已并入
某个已被删除的 `§1` 的话。语域这一条上线时抓出了 48 处第二人称 ——
包括写下这条规则的那份文档。

`npm run verify` 会跑它们。**过不了闸门的文档不算写完。**
