# 文档标准

本文件规定 EaPP 仓库里**怎么写文档**。它是规范性约定 —— 违背它的文档会被要求返工。

---

## 1. 文档分层

这是最重要的一条规则。**规范性**与**非规范性**是硬边界。

```
规范性（normative）       docs/spec/
                         「规则是什么」。唯一裁决者。冲突时以它为准。

非规范性（non-normative） docs/reference/ · docs/guides/ · docs/analysis/
                         docs/CONFORMANCE.md
                         「规则怎么用」「为什么这样定」。解释、索引、举例。
```

由此推出两条禁令：

- **非规范性文档 MUST NOT 引入新规则。** 如果你在写参考页时发现某条语义无处可依，
  那说明规范缺一条 —— 去补规范，不要在文档里发明它。
- **非规范性文档 MUST NOT 逐字复制规范正文。** 复制会分叉；
  规范改了而复制没改，读者就拿到了两个互相矛盾的"权威"。

---

## 2. 四种文档各自的职责

| 文档 | 读者的问题 | 组织方式 | 允许推测吗 |
|---|---|---|---|
| `docs/spec/` | 规则是什么？ | 按协议结构 | 否，MUST/MUST NOT |
| `docs/reference/` | 这个字段到底是什么意思？ | **按实体**，一实体一页 | 否，只陈述 |
| `docs/guides/` | 我要做 X，怎么做？ | **按任务** | 可以，但须标注 |
| `docs/CONFORMANCE.md` | 实现到什么程度了？ | 按层，带数字 | 否，只报告已测事实 |

**参考页与指南都不许说"应该可以"。** 只有两种状态：已验证、未验证。

---

## 3. 参考页必须遵循模板

见 [`docs/reference/_TEMPLATE.md`](reference/_TEMPLATE.md)。固定结构：

```
元数据表    层 · 规范小节 · 实现文件 · 测试文件 · 稳定度
签名        接口与字段表
语义        它做什么，边界在哪
不变量      ID · 规则 · 对应测试
错误        码 · 触发条件 · retryable
示例        可运行代码
相关        交叉链接
```

读者应当能在 30 秒内回答四个问题：
**它是什么 / 怎么用 / 什么时候会失败 / 这条规则写在哪份规范的哪一条。**

---

## 4. 每条规则都要落到一个测试

v3.0 §19.2 是冻结条款：*每个不变量 MUST 至少有一个对应的测试用例。*

因此参考页的「不变量」表格里，**每一行 MUST 给出一个真实存在的测试名**：

| ID | 规则 | 测试 |
|---|---|---|
| `CG-6` | 被 nack 或 claim 超时的位置 MUST 重新对该组可用 | `interaction.test.ts` › `CG-6: an expired claim returns…` |

**落不到测试的规则，要么没被实现，要么不该写在那里。** 两种情况都要处理，不许留空。

---

## 5. 语言与语气

- **正文中文；标识符、代码、RFC 2119 用语保持英文。**
  写 `MUST` / `SHOULD` / `MAY`，不写"必须"/"应该"—— 它们是术语，不是修辞。
- **不使用第二人称。** 不说"你可以调用……"，直接说"调用方 MUST 先……"。
  规范语气描述的是约束，不是建议。
- **一句话一个判断。** 中文长句在规范里是债务。
- **不用夸张词。** 不写"极其强大"、"完美解决"。协议文档要能被信任。

---

## 6. 交叉引用

- 实体名第一次出现时，链接到它自己的参考页。
- 提到规范条款时，给出**具体小节号**，不是"详见规范"。
- 提到实现时，链接到**文件**，不是目录。
- **链接闸门会检查每一条相对链接**：

```bash
pnpm run check:docs
```

外部 URL 不检查 —— 网络失败不该让 `verify` 因为与本次改动无关的原因变红。

---

## 7. 示例

- **必须可运行。** 伪代码会腐烂；真代码不会。
- 示例用真实的导出名与签名。不确定就去读实现，不要猜。
- 教程里的示例应当能直接粘进文件跑起来。
- 不要承诺规范里没有的能力 —— 尤其不要承诺
  [`CONFORMANCE.md`](CONFORMANCE.md) §6 里明确列为"未实现"的东西。

仓库自带的示例在 [`examples/`](../examples/README.md)，它们比"能跑"多一条义务：

- **MUST 自检并核对结论。** 只打印日志的示例坏掉时是静默的 —— 版本变了、默认值改了，
  它照跑不误，而引用那段输出的文档就成了假的。所以每个示例结尾都有一组断言，
  核对的是返回值、派生状态、错误码这些**看不见**的东西，失败即以非 0 退出。
- **MUST 被类型检查覆盖。** `tsconfig.json` 的 `include` 含 `examples/**/*.ts`，
  所以签名一变，示例先红。
- **MUST 在 `pnpm run verify` 里被执行**（`pnpm run examples`）。跑不起来的示例不算示例。
- **文档 MUST NOT 引用一段没跑过的输出。** 引用就贴真实输出，并说明 id 这类值会变。
- **不确定的地方要写出来。** 示例不是宣传材料：如果某条语义有代价（例如
  `ConsumerGroup` 只保证排他、不保证公平），示例里要直说。

---

## 8. 目录与命名

```
docs/reference/   小写短横线，实体名        identity.md · consumer-group.md · state-cell.md
docs/guides/      小写短横线，动词短语      write-a-plugin.md · getting-started.md
docs/spec/        版本号-层名               v3.0.0-core.md · v3.2.0-state.md
```

`_` 前缀表示模板或草稿，**不进索引**。

---

## 9. 修改文档时同步什么

| 改了 | 必须同时更新 |
|---|---|
| 规范条款 | `docs/spec/CHANGELOG.md` + 对应参考页 + 不变量测试 |
| 不变量 ID | 测试名 + `tools/check-invariants.mjs` 的提取结果 + 参考页表格 |
| 实现签名 | 对应参考页的「签名」小节 |
| 偏离规范 | `docs/CONFORMANCE.md` §5 |
| 新增实体 | `docs/README.md` 的索引表 + 参考页 + 规范小节 |

---

## 10. 闸门

文档不是靠自觉维持的。仓库里的闸门：

```bash
pnpm run check:invariants   # 每条不变量都有测试；无空测试体
pnpm run check:docs         # 链接解析 / 正文语域 / 参考页结构
pnpm run check:duplicates   # 同一类型在多处复述时，成员类型一致
```

`pnpm run verify` 会跑它们。**过不了闸门的文档不算写完。**

三道文档闸门各查一件事，每一件都曾在此规则被写下之后、却无人执行的情况下失效过：

| 闸门 | 检查什么 |
|---|---|
| 链接 | 每条相对链接落到真实文件 |
| 语域 | 代码块之外不出现第二人称、口语标记或否定式排比（本文件 §5） |
| 参考页结构 | 每页具有 §3 规定的元数据表与六个小节 |
| 副本 | 同名类型在两个以上文档中出现时，**两边都有的成员**其类型必须一致；只出现在一边的成员视为节选，不报 |

**副本闸门的存在理由。** §1 禁止逐字复制规范正文，但**改写**同样会漂移 ——
参考页为了省去读者翻页而复述类型定义，规范一改，复述就成了假话。
`Discovery` 一页曾把 `Criteria.version` 写成"只支持精确值与 `*`"，
而那正是勘误 E-E 修掉的东西。逐字比对会误报（节选、类型别名都是合法的），
所以它只比**两边都有**的成员。

闸门检查的都是**无歧义的标记**，不是文风的全部 —— 判断性的部分仍然靠评审。
