## 1. 问题

在 `3.5.0` 落笔之前，规范定义了 **36 个错误码**，却只规定其中 19 个在什么情况下产生。
（本提案已落笔，因此这段描述在今天的工作树上**无法复现**；它记录的是提出时的状态。）

剩下 17 个 ——

```
EAPP_IDENTITY_INVALID        EAPP_IDENTITY_DUPLICATE      EAPP_CAPABILITY_NOT_FOUND
EAPP_CAPABILITY_NOT_EXPOSED  EAPP_PLUGIN_NOT_FOUND        EAPP_PLUGIN_INACTIVE
EAPP_LIFECYCLE_INVALID       EAPP_DISCOVERY_SCOPE_INVALID EAPP_INTERNAL
EAPP_CHANNEL_INVALID         EAPP_CHANNEL_CLOSED          EAPP_CHANNEL_DRAINING
EAPP_CURSOR_INVALID          EAPP_SUBSCRIPTION_INVALID    EAPP_LEASE_EXPIRED
EAPP_LEASE_CONFLICT          EAPP_STATE_KEY_INVALID
```

—— 只出现在错误模型的清单里，正文的任何地方都没有说它们何时 MUST 被返回。

**规范实际留下了什么缺口。** 两个实现可以各自为同一个码规定不同的条件，而都自称合规：
合规的判据是不变量，而不变量没有提到这些码。

| | 实现 A | 实现 B |
|---|---|---|
| `bind` 的目标 Plugin 不存在 | `EAPP_PLUGIN_NOT_FOUND` | `EAPP_BINDING_INVALID` |
| 能力名拼错 | `EAPP_CAPABILITY_NOT_FOUND` | `EAPP_CAPABILITY_NOT_EXPOSED` |
| 向已 CLOSED 的 Channel 发消息 | `EAPP_CHANNEL_CLOSED` | `EAPP_CHANNEL_INVALID` |
| 同一位置被两个消费者认领 | `EAPP_LEASE_CONFLICT` | `EAPP_CHANNEL_DRAINING`（若它把 Channel 状态当作条件） |

两者都满足全部 221 条不变量。调用方依据错误码分支的代码，在这两份实现之间无法通用 ——
而错误码的全部用途就是给调用方一个可以分支的信号。

**这不是假想。** 另外 19 个码之所以有触发条款，是因为它们恰好被写在某条不变量里
（`CC-6` 规定 binding 不存在时返回 `EAPP_BINDING_INVALID`，等等）。
剩下 17 个之所以没有，是因为**没有一条不变量恰好提到它们** —— 缺口不是判断失误，
是"码表"与"规则"这两份清单从未被对账过。

---

## 2. 提案

在三个分卷的错误模型里各增加一张 **「本层错误码与它们的产生条件」** 表，
逐条给出该码何时 MUST 被返回，并引用它所依据的条款。

```text
ER-1  实现为一个条件返回的错误码 MUST 是规范为该条件规定的那个码。
ER-2  每个在附录 D 中登记的错误码 MUST 在正文中被某一条款规定其产生条件。
```

配套：

- 附录 D 不再自行分类，改为**登记表 + 指向条件的节号**。条件只有一处 ——
  写在使用它的规则所在的分卷；附录只回答「一共定义了哪些码」。
- `check:spec` 增加第八条规则，机械检查 `ER-2`：附录 D 里出现的每个码 MUST 也在正文里出现。
- `EAPP_INTERNAL` 的条款写成兜底形式：**MUST NOT** 用它替代规范已为某种情况规定的码。
  它是唯一一条无法正面给出条件的条款，因而不假装能给出。

---

## 3. 为什么不维持现状

**不采纳的代价可以精确计量。** 错误码是调用方唯一的机器可读信号。
一个没有规定产生条件的码，在调用方看来与「成功」以外的任意状态没有区别。

**已经发生过的情形。** 编写 `docs/guides/write-a-plugin.md` 时，作者试图为每一个码
给出「何时出现」，结果发现 17 个码没有任何可引用的条款；它只能另列一张
「只登记、没有触发条款」的清单。也就是说，**读者第一次需要这份信息时，
规范就没有提供它**。

**若只是"将来可能"，为什么它一定会发生。** 每份实现都会为自己的错误路径选择码，
而选择依据是码的**名字**。名字相同、理解不同的情况必然出现 ——
`EAPP_CAPABILITY_NOT_FOUND`（能力不存在）与 `EAPP_CAPABILITY_NOT_EXPOSED`（能力存在但未暴露）
的边界尤其容易分叉，因为「不存在」与「未被暴露」在只看到一次调用失败时无法区分。

## 4. 对既有实现的影响

| 实现 | 会变成不合规吗 | 需要改什么 |
|---|---|---|
| TypeScript 参考实现（`reference` 分支，三层） | **可能** | 它选择了码，但选择依据是它自己的错误路径。需要逐条核对 §18 / §33 / §47 的三张表，把不一致处改过来 |
| Go 实现（`reference` 分支，Composition Core + Interaction） | **可能** | 同上 |
| 本次独立性实验的两份实现 | 是 | 它们按 `3.5.0` 的正文写出，因此是本提案的**第一批**验证对象 |

**这是一次传递性的合规收紧**，故归类为 `3.x.0` 而非 `3.0.x`：
在补上条款之前，两种做法都合规；补上之后只剩一种。

## 5. 一致性

| 不变量 | 规则 | 如何被判定 |
|---|---|---|
| `ER-1` | 实现必须使用规范为该条件规定的码 | 实现方的测试：为每个条件构造输入，断言返回的码。**无法机械检查** —— 见 §7 |
| `ER-2` | 每个登记码都有产生条件 | `check:spec` 第八条规则：附录 D 的每个码 MUST 也在正文中出现 |

`ER-2` 是可判定的，因此它是一条真正的闸门。`ER-1` 不是 —— 它约束实现的行为，
而不是文本的性质。把这两件事分开写，是为了不把「闸门通过」误当作「实现正确」。

## 6. 被否决的替代方案

**A. 把 17 个码从登记中移除。**
否决理由：实现仍然需要这些失败信号（`EAPP_PLUGIN_NOT_FOUND` 没有替代品）。
移除只是把问题从规范推回给实现，而且会让已经使用这些码的实现失去一个合法名字 ——
它们仍会返回同样的字符串，但那个字符串不再有任何规范含义。

**B. 保留登记，声明"实现 MAY 自行规定条件"。**
否决理由：那正是缺口本身。跨实现分支持错误码的意义在于码的含义由规范固定。

**C. 由附录 D 直接给出全部条件。**
否决理由：条件属于规则，规则写在分卷里。若附录也写一份，就有两处内容需要同步 ——
这正是本次修订要消除的那类问题。附录只做登记。

**D. 只给最常遇到的几个码补条件，其余保留。**
否决理由：留下的是「哪些码有规定、哪些没有」这个需要读者自己查的问题，
而它正是缺口的形式。

## 7. 未解决的问题

1. **评审未取得。** 本文与 `3.4.0` 的分卷 IV 都处于「正文已落笔、§2.3 的评审尚未发生」
   的状态。两处事实并列写在规范元信息的状态行与 `CHANGELOG.md` 里，而不是靠评审通过追认。

2. **`ER-1` 无法被闸门检查。** 它约束实现，不约束文本。收口解决的是
   「条件是否被写下来」，不是「实现是否照做」。

3. **有几条条件是从相邻条款推出的，不是从一条直述的规则中读出的。**
   尤其需要评审逐条核对的是：

   - `EAPP_CAPABILITY_NOT_FOUND` 与 `EAPP_CAPABILITY_NOT_EXPOSED` 的边界
     （前者是"任何已注册 Plugin 都没有这个能力"，后者是"提供方没有暴露它"）。
   - `EAPP_PLUGIN_INACTIVE` 只覆盖 INACTIVE，SUSPENDED 的情况由 `LC-6` 的
     `EAPP_LIFECYCLE_INVALID` 承担 —— 这个划分是本次作出的，规范此前没有表态。
   - `EAPP_TIMEOUT` 归在 Interaction Layer，而它同时也是插件的调用操作（§52）会遇到的码。

4. **`retryable` 只对 `EAPP_REVISION_CONFLICT` 规定为 `true`。**
   其余码是否都应为 `false`，本提案未逐一表态，沿用了「缺省 `false`」这条规则。
   若评审认为某些码（例如 `EAPP_CHANNEL_DRAINING`）应当可重试，那是一次独立的小修订。

## 8. 评审记录

**评审 A —— 独立实现者，覆盖第 I 部分。结论：`Accept with changes`。**

它核对无误的部分：36 个码与当时 221 条不变量逐条对上；规范元信息与 `CHANGELOG.md`
对"评审尚未取得"的表述一致；`ER-2` 是一条可判定的真闸门。

它要求改动的：

| # | 问题 | 处置 |
|---|---|---|
| 1 | `EAPP_PLUGIN_INACTIVE` 的条件**自指** —— 全文唯一"要求 Plugin 处于 ACTIVE"的操作就是它自己。后果是 `ER-2` 通过，而 `ER-1` 无任何测试可满足或违反 | 已在 `3.6.0` 标注为不可达 |
| 2 | `EAPP_TIMEOUT` 的归属与本文 §2 自定的"条件只写在归属分卷"冲突 | 已在 `3.6.0` 改正 |
| 3 | `EAPP_IDENTITY_INVALID` 未覆盖 `instance` 为空与 `ID-6` | 已在 `3.6.0` 补齐 |
| 4 | `C-1` / `C-2`（能力名为空、版本非 SemVer）没有码 | 已在 `3.6.0` 并入 `EAPP_CAPABILITY_NOT_FOUND` |
| 5 | `EAPP_BINDING_CLOSED` 与 `O-4` 的幂等冲突，在它的实现里不可达 | **不成立** —— 该码由 §32 的 `CC-7` 产生；评审者的实现只覆盖第 I 部分，故在它那里不可达 |
| 6 | `NOT_FOUND` 行按"已注册"判，`PLUGIN_NOT_FOUND` 行按"当前 Trust Scope"判，而 §12.2 的 `bind` 没有 scope 参数 | **未处理** |
| 7 | §1 描述的是落笔前的正文 | 已加限定（见 §1） |
| 8 | `ER-1` 无法机械检查 | **未处理**。它建议：按码表机械生成"为每个条件构造输入、断言返回的码"的用例，放进 `reference` 分支的 driver 协议 —— 那样 `ER-1` 就从"实现自觉"变成"可查" |

**评审 B —— 尚未取得。** §2.3 要求两名独立实现者。
