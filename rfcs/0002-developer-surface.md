## 1. 问题

本文件的六章正文规定了插件的组合、互动与状态共享**语义**，但没有规定这些语义以什么**形状**暴露给插件作者。
在此之前，"插件作者面对什么"只存在于本仓库的参考实现里：`packages/runtime` 把若干操作封装为一个门面，
而这份包不构成规范的一部分。`docs/spec/` 中检索"五个操作"没有任何结果。

**规范实际留下了什么缺口。** 两份互不相识的实现可以各自理解全部语义、各自合规，却无法让插件互通：

| | 实现 A | 实现 B |
|---|---|---|
| 发现 | `find(criteria, scope)` | `discover(filter)` |
| 连接 | `bind(request)`，`request.from` 是提供方 | `connect(consumer, provider, capability)` |
| 调用超时 | 返回 `{ ok: false, error: { code: 'EAPP_TIMEOUT' } }` | 抛出一个异常，或以 `null` 表示 |
| 调用的方向 | `from` 指被调用方 | `from` 指调用方 |

两者都满足 `O-1`–`O-8`、`RQ-1`–`RQ-4` 与全部其余不变量。它们的插件必须为彼此各写一份适配层 ——
而这正是"任何语言、任何运行时、任何传输，只要实现这些语义，就能互通"所要避免的成本。

**这不是假想。** 本项目自己的两份实现之间已经发生过这类分歧：一处 `invoke` 的 `from` / `to` 方向在
指南中写反过，两处 `watch()` 的同步 / 异步形态在规范与实现之间不一致过（后者由 `SUB-9` 与 `SW-9` 逼出）。
两处都是在**没有任何条款被违反**的情况下产生的 —— 因为没有任何条款规定形状。

---

## 2. 提案

新增**第 IV 部分"插件开发表面"**（§50–§54），共 5 节、9 条不变量、5 个合规等级。

```text
OP-1   表面 MUST 只由本协议规定的操作组成。
OP-2   五个操作的参数与结果的类型 MUST 全部在本协议内定义；
       插件作者 MUST 无需访问实现的内部对象即可完成组合、互动与调用。
OP-3   表面 MUST NOT 引入本协议未定义的语义。表面是前三部分的剖面，不是第四层。
OP-4   bind 的 from MUST 是提供 Capability 的一方；invoke 的 from MUST 是调用方。
       两个操作的 to MUST 指向同一方。
OP-5   invoke MUST 携带关联标识；截止时间到达时 MUST 以 EAPP_TIMEOUT 结束，
       MUST NOT 静默挂起，MUST NOT 返回形态未定义的值。
OP-6   activate / deactivate / suspend / resume 的语义 MUST 与 §10 一致；
       suspend MUST NOT 断开 Binding。
OP-7   同一组合语义的两份实现 MUST 能只经由表面互通：表面 MUST NOT 要求实现特有的握手、
       能力协商或序列化约定。
OP-8   find 的结果 MUST 可直接作为 bind 与 invoke 的输入，
       MUST NOT 需要额外的注册、转换或转写步骤。
OP-9   声明 C1、C2、C3、I1 或 I6 中任一等级的实现 MUST 同时声明由它蕴含的表面等级。
```

配套：

- 五个**操作组**（发现 / 连接 / 激活 / 通信 / 调用），每组只含正文已定义的操作，命名为 §51 的表。
  四个组**不新增语义**，只是把已有操作归类并固定其可寻址名称。
- **`invoke` 是新操作**。请求-应答此前只有信封（`RequestMessage` / `ResponseMessage`）与规则
  （`RQ-1`–`RQ-4`），没有一个是操作。`invoke(from, to, capability, request, options)` 是那个名字。
  其语义全部由 `RQ-1`–`RQ-4` 给出；本提案只补上操作名、参数表与超时错误码 `EAPP_TIMEOUT`
  （该码自 `3.1.0` 起已存在，因此不需要新增错误码）。
- 合规等级 `CS1`–`CS5`，并在 §3.2 的 `ConformanceClaim.levels` 取值域中扩充这五个名字。

## 3. 为什么不维持现状

**不采纳的代价可以精确计量：每多一份实现，就多一次适配。** 两实现互通需要 1 份适配层，三份需要 3 份，
`n` 份需要 `n(n-1)/2` 份。协议的价值恰好在于把这个二次项压成常数。

**已经发生过的三次。** 前两次写在 §1 的表里；第三次是本项目最贵的一次：Go 实现者依规范正文独立实现
Interaction 层时，被迫自行裁定 **10 处规范留白**，其中数处正是形状问题：

```
ConsumerGroup 的起始位置            → 选了 earliest retained，而非 head
DL-3：at-most-once 下 ack 该做什么  → 选了"无害并结算"
resume() 是否回退到已确认位置        → 选了不回退
```

这些裁定**都记在它的回报里，但没有写进任何规范文本**。也就是说：第二份实现之所以能与第一份在同一批
黑盒检查下同时通过，靠的是两处巧合加上一批未记录的默契，而不是规范的约束力。

**若只是"将来可能"，为什么它一定会发生。** 表面不存在时，实现者唯一的参照是**自己**；
每份实现都会合理地做出自己的选择。这与实现者的水平无关，与规范是否含糊有关。

## 4. 对既有实现的影响

| 实现 | 会变成不合规吗 | 需要改什么 |
|---|---|---|
| TypeScript 参考实现（`reference` 分支，三层完整） | 否 | `@eapp/runtime` 的公开方法已与 §51 的表一一对应；需按 `OP-*` 补测试，并把 `levels` 声明扩为含 `CS1`–`CS5` |
| Go 实现（`reference` 分支，Composition Core + Interaction） | **是，但不因为它做错了什么** | 它未声明任何 `CS` 等级。`OP-9` 生效后，声明 `C1`–`C3` 的它 MUST 声明 `CS1`–`CS3` —— 这需要它按 §51 的名字重命名若干导出名，或补一层薄门面 |
| 任何声明 `C1`–`C3` / `I1` / `I6` 的第三方实现 | 同上 | 未声明 `CS` 等级的实现由 `OP-9` 变为不合规 |

**这是一次传递性的合规收紧，须在协议版本上体现**，故归类为 `3.x.0` 而非 `3.0.x`。

## 5. 一致性

| 不变量 | 规则 | 测试 |
|---|---|---|
| `OP-1` | 表面只含协议规定的操作 | 表面不得导出任何未在 §51 出现的操作名 |
| `OP-2` | 参数与结果的类型全部在协议内定义 | 对 `find` / `bind` / `createChannel` 的结果做结构断言，不使用实现内部对象 |
| `OP-3` | 表面不引入新语义 | 表面调用的可观察效果与直接调用各层操作一致 |
| `OP-4` | `bind` / `invoke` 的方向 | `bind(P, C)` 后 `invoke(from = C, to = P)` 成功；反向失败 |
| `OP-5` | 超时 | 对不响应的对端调用 `invoke`，在 `timeoutMs` 后得到 `EAPP_TIMEOUT`，且不挂起 |
| `OP-6` | 生命周期语义 | `suspend` 后 Binding 仍存在且为 DORMANT 派生 |
| `OP-7` | 互通 | 两份实现在同一批黑盒检查下通过 —— 即 `reference` 分支上的 driver 协议与检查工具 |
| `OP-8` | 发现结果可直接使用 | `find` 的返回项直接作为 `bind` 的输入，无中间步骤 |
| `OP-9` | 等级蕴含 | 一致性声明中，声明 `C1`–`C3` / `I1` / `I6` 的实现必须同时含对应 `CS` 等级；由声明校验器拒绝缺失 |

`OP-7` 是其中唯一**无法由单份实现验证**的一条：它需要两份从规范正文独立写出的实现同时通过一批
不属于任何一方的检查。本项目已有该装置（driver 协议 + 黑盒 harness），因此这一条是可执行的，
而不是一句愿望。

## 6. 被否决的替代方案

**A. 把表面写成非强制（`SHOULD`）的推荐形状。**
避免抬升协议版本，也避免让既有实现失去合规。否决理由：`SHOULD` 意味着两份实现可以各自选择，
于是 §1 的缺口原样保留 —— 一个不强制统一的形状不能换来互通，而互通是这一章存在的全部理由。

**B. 由参考实现的门面包充当规范。**
即现状。否决理由：这让"实现本协议"变成"使用本仓库的代码"，与协议的语言中立性直接冲突。
第三方实现者会被迫阅读一份 TypeScript 包来了解自己该实现什么。

**C. 定义一个独立的 IDL 或机器可读接口描述。**
否决理由：这会把"读一份规范"变成"读规范加一个格式",并引入工具链依赖。
本提案改用 §1.2 的记法与逐字段表格，效果相同而成本更低。

**D. 把表面做成第四层。**
否决理由：第四层意味着新的本体与单向依赖，而这会改变分层方向 —— 属于 `4.0.0`，
且没有任何语义上的必要。表面不定义新本体，它是剖面。

**E. 只规范化"调用"，不碰其余四组。**
否决理由：`invoke` 确实是缺口最深的一处，但发现与连接的结果形状同样是跨实现契约。
只修一处会让其余四组的分歧被这一处的确定性掩盖。

## 7. 未解决的问题

1. **评审未取得。** 本文处于 `Review`，但 §2.3 要求的两名独立实现者评审**尚未发生**。
   规范正文已按本提案落笔（协议版本 `3.4.0`），这一事实在 §2 的状态行与变更记录中并列写明，
   而不是靠评审通过来追认。将实现移出主仓库后，`reference` 分支的两份实现是候选评审方；
   它们都需要先同步到 `3.4.0` 的正文。

2. **`OP-9` 的时间线。** 它使一批既有实现立即失去合规。是给一个宽限期（例如在 `3.4.0` 内只警告、
   自 `3.5.0` 起强制），还是立即强制，未定。倾向立即强制：分级执行会让"声明"这一动作失去确定性。

3. **`invoke` 与 `send` 的关系未定死。** 本提案规定 `invoke` 的语义等于"在 request 模式 Channel 上
   发一个请求并等待应答"，但未规定它 MUST 由 `send` + 关联标识实现，还是 MAY 由实现直接完成。
   两种都满足 `RQ-1`–`RQ-4`。若后续需要，可在 `OP-*` 中补一条。

4. **State 模式的操作未纳入表面。** 含 `state` 模式的 Channel 复用 `send` / `subscribe` / `ack`，
   但 `set` / `delete` / `watch` / `snapshot` 本身没有对应的 `CS` 等级。是否补 `CS6` 尚未决定；
   本提案选择留白并写明，而不是先给一个还没想清楚的等级编号。
