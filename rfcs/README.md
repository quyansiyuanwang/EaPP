# 规范变更提案（RFC）

本目录存放对**冻结规范**的变更提案。

规范 §2.3 规定，任何拟议变更 MUST 提交至规范仓库并经评审。本目录是那条规定
的落点 —— 在此之前它没有落点，因此无法执行。

---

## 1. 什么需要提案

判据是**是否改变语义**，与改动大小无关。

| 变更 | 走哪里 |
|---|---|
| 新增不变量、新增合规等级、新增错误码、新增分卷或章节 | 本目录。§2.1 归类为 `3.x.0` |
| 修改任一既有不变量、修改分层方向、修改核心概念、修改操作语义 | 本目录。§2.1 归类为 `4.0.0` |
| 澄清歧义文本、修正拼写与格式、补充非规范附录 | 不走本目录。§2.4 的勘误，就地写入正文并在 [`CHANGELOG.md`](../CHANGELOG.md) 留一条 |

**边界情况**：若一处"澄清"会使两个原本都能自称合规的实现变成只有一方合规，
它改变的是语义，走提案。

---

## 2. 提案的生命周期

```
Draft ──► Review ──► Accepted ──► Implemented
  │          │           │
  └──────────┴───────────┴──► Rejected / Withdrawn
```

| 状态 | 含义 |
|---|---|
| **Draft** | 作者正在写。尚未请求评审 |
| **Review** | 已请求评审，等待 §2.3 要求的评审意见 |
| **Accepted** | 评审通过，裁定已定。规范正文尚未修改 |
| **Implemented** | 已写入规范正文，协议版本已按 §2.1 更新 |
| **Rejected** | 评审未通过。**文件保留**，并须写明替代路径 —— 否决的理由比提案本身更有用，它记录了什么不可以再提一次 |
| **Withdrawn** | 作者撤回 |

**Accepted 与 Implemented 分开**是有意的：裁定与落笔是两件事，前者可能远早于后者。
只有 `Implemented` 的提案才构成规范的一部分。

**被否决不等于问题不成立。** 提案可能在评审中被证明过于宽泛、无法执行，或把几个正交的
问题捆在一起。此时正确的结果是 `Rejected` 加一条更小的替代路径 —— 而不是把提案
改到能被通过为止。

---

## 3. 评审要求

规范 §2.3 要求**至少两名独立实现者**评审。此处的"独立"指：

- 不是提案作者；
- 各自维护一份 EaPP 实现。

**当前状态。** 实现不在本仓库，而在 `reference` 分支上：一份 TypeScript 参考实现（三层完整），
一份 Go 实现（Composition Core 与 Interaction Layer）。因此：

```
Composition Core 的变更      两份实现都在，可取得两份评审
Interaction 的变更           两份实现都在，可取得两份评审
State Mode 的变更            只有一份实现覆盖，只能取得一份
插件开发表面（第 IV 部分）     涉及前三部分的多组等级，可取得两份
```

在只有一份实现的层上，提案 MUST 在状态行注明评审的实际状态。这是一项**已知限制**，
不是豁免 —— 它使缺口可见，而不是让评审要求被静默地绕过。

**未能取得评审时，缺口写在两处**：本目录的状态表，与规范元信息的状态行。
两处必须反映同一个事实。

---

## 4. 一份提案必须回答的问题

模板见 [`0000-template.md`](./0000-template.md)。必答项：

1. **§2.1 归类**：`3.0.x` / `3.x.0` / `4.0.0` 中的哪一类，以及理由。
2. **改变什么语义**：改前与改后，各自如何判定。
3. **为什么不能是现状**：不采纳会怎样 —— 这类问题此前**实际发生过**吗？
   发生了就给出具体例子。
4. **对既有实现的影响**：哪些实现会从合规变成不合规。
5. **一致性如何验证**：新增或修改哪条不变量，以及它如何被从外部判定（§3.1 要求每条不变量
   至少一个测试用例，测试属于实现方）。
6. **`eappVersion` 的变化**：协议版本是否因此改变，以及不实现该变更的实现应报告什么。

---

## 5. 落笔

提案被 `Accepted` 之后：

1. 修改 [`docs/spec/eapp.md`](../docs/spec/eapp.md)；
2. 在 [`CHANGELOG.md`](../CHANGELOG.md) 登记，并给出协议版本的变化；
3. 跑 `npm run verify` —— [`check:spec`](../tools/check-spec.mjs) 会拒绝"写了不变量
   而正文没有陈述"的状态，也会拒绝悬空的 `§` 引用；
4. 更新受影响的参考页与指南。参考页是索引页，因此多数改动只需改其中的 §号；
   复述过被改内容的指南由人负责同步；
5. 把提案的状态改为 `Implemented`，并注明协议版本。
